# 02 · 技术路线：为什么走 AppleALC 注入

## 1. 三条可选路线对比

| 路线 | 做法 | 评价 |
|---|---|---|
| **A. AppleALC 配置注入** ✅ 采用 | 从 Linux 驱动/社区提取 SN6140 的 verb、pin、layout 配置，做成 AppleALC 认识的 layout 数据，复用原生 AppleHDA | 音质、睡眠唤醒、音量控制全原生；社区已验证；最稳 |
| B. VoodooHDA 式代码移植 | 把 ALSA HDA 的 C 代码真正移植成独立 kext | 需重写整套音频栈（verbs/DMA/PCI），与 AppleHDA 冲突；macOS 15 支持差；音质差 |
| C. 从零写独立 kext | 基于 IOAudioFamily / AudioDriverKit 自己实现控制器+codec | 学术价值高，实用价值低，周期极长；macOS 15 已废弃 IOAudioFamily、转向用户态 AudioDriverKit |

## 2. 为什么不直接移植 Linux ALSA 代码

- ALSA 的 HDA 驱动依赖整套 Linux 内核音频栈（`snd_hda_core`、verbs、DMA、PCI）。照搬过来等于写一个和 AppleHDA 并行且冲突的音频栈。
- VoodooHDA 就是这条路，但对 Sequoia 支持很差。
- `IOAudioFamily` 在 macOS 15 已废弃，Apple 转向用户态 AudioDriverKit，从零写 kext 的技术窗口已经关闭。

**真正可行的「移植」是移植配置数据，不是移植 C 代码。**

## 3. AppleALC 注入方案原理

```
OpenCore 引导
   │
   ├─ Kernel>Add 注入 Lilu.kext（补丁引擎，必须排在 AppleALC 前）
   ├─ Kernel>Add 注入定制 AppleALC.kext（内含 SN6140 layout 15 资源）
   ├─ NVRAM boot-args: alcid=15 alcdelay=1000
   └─ DeviceProperties: HDEF 的 layout-id / alc-layout-id = 15
                    │
                    ▼
AppleALC 挂钩 AppleHDA，把 layout 15 的 verb/pin 配置喂给原生驱动
                    │
                    ▼
AppleHDADriver 成功匹配 SN6140 → 扬声器 / 耳机 / 麦克风 / 热插拔全部工作
```

为什么是 layout 15：社区（`chenhggu6475/Senary-SN6140-AppleALC-Hackintosh`）在同款 `14f1:1f87` rev `0x100100`、同款 macOS 15.8.1 上验证 `layout 15` 可让内置扬声器、麦克风、耳机热插拔全部工作。配置资源位于 [../01-driver/source/Resources/SN6140/](../01-driver/source/Resources/SN6140/)。

## 4. 本工程采取的具体动作

1. **替换 kext**：官方 AppleALC 1.9.8（不含 SN6140）→ 定制版 1.9.9（`DBG-199-2026-10-26`，二进制内含 SN6140 数据）。
2. **改 boot-args**：`alcid=11` → `alcid=15`，加 `alcdelay=1000`（给 codec 初始化留出延时）。
3. **改 layout-id**：HDEF 的 `layout-id` / `alc-layout-id` 从 int 11 → data 15。
4. **禁用冲突 kext**：`SimpleHDA.kext` 与 AppleALC 抢同一个 HDA 控制器，必须关闭。
5. **保证顺序**：`Lilu.kext` 必须排在 `AppleALC.kext` 之前。

每一步都由 [../02-efi-oc/deploy_sn6140.py](../02-efi-oc/deploy_sn6140.py) 自动完成，并带备份/回滚。详见 [03-OpenCore配置说明](03-OpenCore配置说明.md)。
