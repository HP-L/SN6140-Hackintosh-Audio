# 01 · Hardware Diagnosis and Conclusions

> English version of [01-硬件诊断与结论.md](01-硬件诊断与结论.md).

## 1. The Starting Problem

User report: Hackintosh has no audio, believed to be an "SN6180 sound card", hoping to port a Linux open-source driver into a kext.

## 2. Diagnosis Process (Measured)

### 2.1 At the system level

```bash
system_profiler SPAudioDataType       # Devices list is empty — no audio device at all
kextstat | grep -i -E 'audio|hda'     # AppleHDA / AppleHDAController / IOHDAFamily all loaded
```

The key contradiction: **the AppleHDA driver stack is loaded, but no audio device appears**. This means the controller is detected, but the codec has not matched any driver.

### 2.2 Reading the real codec ID from IORegistry

```bash
ioreg -r -c IOHDACodecDevice -l
```

Read:

```
IOHDACodecVendorID   = 351346567
IOHDACodecRevisionID = 1048832
```

Precise conversion (mental math is error-prone — always use a tool):

| Decimal | Hex | Meaning |
|---|---|---|
| 351346567 | `0x14F11F87` | **This machine's codec = SN6140** |
| 1048832 | `0x100100` | revision |
| 351346897 | `0x14F120D1` | SN6180 (**not** this machine) |

> ⚠️ During the process it was briefly misjudged as SN6180 by mental math, later corrected by precise Python conversion. **Hardware truth comes from IORegistry measurements.**

### 2.3 Root cause confirmed

```
AppleHDACodecGeneric / AppleHDADriver already created under IOHDACodecFunction
but status is !registered, !matched
```

- The AppleHDA binary does **not** contain SN6140 configuration
- Official AppleALC's 111 supported codec families do **not** include SN6140/SN6180
- Boot args originally had `alcid=11`, but AppleALC doesn't recognize this codec, so the injection is ineffective

**Conclusion**: the codec hardware is present, but no driver configuration matches it → no sound.

## 3. Chip Identity Comparison

| Model | Vendor:Device ID | Notes |
|---|---|---|
| **SN6140** | `14f1:1f87` | **Measured on this machine**, Senarytech/Conexant family |
| SN6180 | `14f1:20d1` | What the user initially thought; not this machine |
| SN6186 | `1fa8:6186` | The model in Linux mainline `senarytech.c`; not this machine |

All three belong to the Conexant (`0x14f1`) / Senarytech (`0x1fa8`) family and are handled in Linux by `patch_conexant.c` / `senarytech.c`, but their **pin configurations differ and cannot be mixed**.

## 4. Diagnosis Conclusions

1. The real chip in this machine is **SN6140** (`0x14F11F87`), not SN6180.
2. The failure is "**missing configuration**", not "unrecognized hardware" — no need to write a driver from scratch, just supply AppleHDA with a correct layout configuration.
3. The community already has a verified solution for the same codec + macOS 15.8.1 (layout 15), which can be adopted directly, avoiding the high risk of building verb data from scratch.
